# 技术实现

这篇讲三件事：**页面数据怎么拿到**、**「立即沟通」按钮怎么找到并点下去**、
**怎么确认消息真的发出去了**。

一句话概括这个项目的技术取向：**能不解析 DOM 就不解析 DOM，必须解析时也不硬编码选择器。**
原因下面会讲清楚。

---

## 一、为什么不解析列表页 DOM

最自然的想法是：打开搜索页，`querySelectorAll('.job-card-box')`，逐张卡片读岗位名、薪资、公司。
这条路走不通，有两个硬障碍。

### 障碍 1：薪资是字体密文

页面上肉眼看到 `45-75K`，但 `textContent` 取到的是这个：

```python
原文: '-K'
码点: ['0xe033', '0xe036', '0x2d', '0xe035', '0xe031', '0x4b']
```

`U+E033`、`U+E036` 这些落在 Unicode **私有使用区**（Private Use Area, U+E000–U+F8FF）。
这个区间 Unicode 标准不赋予任何含义，留给厂商自定义——BOSS 用一套自定义字体
把 `0-9` 映射到这些码点，浏览器渲染时按字体的字形表画出数字，
但字符本身不携带「这是 4」这个信息。

注意 `-`（0x2d）、`K`（0x4b）、`·`（0xb7）、`薪`（0x85aa）都是明文，
**只有数字被加密**。这是针对性的反爬——他们知道你要的是数字。

理论上可以下载字体文件、解析 `cmap` 表建立映射关系还原数字，但：

- 字体文件是**按会话动态生成**的，映射关系每次刷新都变
- 增加一个 TTF 解析依赖，以及一条完全不可控的失效路径

而同样的数据，接口里是明文：`"salaryDesc": "45-75K"`。

### 障碍 2：有些字段卡片上压根没有

`公司规模`、`技能标签`、以及最关键的**猎头标记**，DOM 里都找不到。
猎头岗在卡片上只有一个左上角的角标图片，标题和公司名完全看不出区别。

接口里这三样都在：`brandScaleName`、`skills`、`proxyJob`/`goldHunter`/`proxyType`。

## 二、旁听接口，而不是构造请求

既然数据在接口里，为什么不直接 POST 那个接口？

因为接口带签名参数（`lid`、`securityId` 之类），自己构造容易对不上，
而且一个只发 XHR、从不渲染页面的客户端，行为特征跟真人差得太远。

**采用的做法是：正常打开页面、正常往下滚，顺手把页面自己发出的响应接下来。**

```python
JOBLIST_API = "/wapi/zpgeek/search/joblist.json"

def _capture_joblist(page, action):
    """执行 action，并接住它触发的那次列表接口响应。"""
    try:
        with page.expect_response(
            lambda r: JOBLIST_API in r.url, timeout=_API_TIMEOUT_MS
        ) as info:
            action()                    # 导航 或 往下滚
        return info.value.json()
    except (PWTimeout, ValueError):
        return None
```

`page.expect_response` 是 Playwright 的网络监听：注册一个匹配函数，
执行动作，然后拿到第一个匹配的响应。请求是**页面自己发的**——
签名、cookie、header 全都是真的，我们只是旁听。

### 翻页靠滚动，不是 page 参数

BOSS 的列表是无限滚动，搜索 URL 里的 `page=` 参数对接口无效。所以：

```python
data = _capture_joblist(page, lambda: page.goto(search_url(...)))   # 第一页：导航触发
...
data = _capture_joblist(page, lambda: human_scroll(page, times=3))  # 后续页：滚动触发
```

`human_scroll` 不是 `scrollTo(0, 99999)`，而是分几次滚、每次距离和间隔都随机：

```python
def human_scroll(page, times=3):
    for _ in range(times):
        page.mouse.wheel(0, random.randint(400, 900))
        page.wait_for_timeout(random.randint(300, 800))
```

用 `page.mouse.wheel` 而非 JS 的 `window.scrollTo`——前者走的是浏览器真实的
输入事件管道，后者是脚本调用，页面脚本能分辨。

### 接口字段到 Job 的映射

```python
def parse_api_job(raw: dict, keyword: str) -> Job | None:
    job_id = (raw.get("encryptJobId") or "").strip()
    title  = (raw.get("jobName") or "").strip()
    if not job_id or not title:
        return None          # 关键字段缺失就丢掉，不硬撑
    return Job(
        job_id=job_id,
        url=f"{BOSS_HOME}/job_detail/{job_id}.html",   # 详情页 URL 是拼出来的
        salary_text=raw.get("salaryDesc"),             # 明文！
        company_size=raw.get("brandScaleName"),        # DOM 里没有
        skills=raw.get("skills") or [],                # DOM 里没有
        is_headhunter=bool(                            # DOM 里没有
            raw.get("proxyJob") or raw.get("goldHunter") or raw.get("proxyType")
        ),
        job_type=int(raw.get("jobType") or 0),         # 5 = 在校/应届
        ...
    )
```

`is_headhunter` 取三个字段的或，是因为实测它们总是一起出现（同为 1 或同为 0），
但不保证接口哪天只给其中一个。

**详情页 URL 不从 DOM 里取 href，而是用 `encryptJobId` 拼**——少一次 DOM 依赖。

### DOM 解析作为兜底保留

`parse_card` / `scrape_page` 仍在代码里，接口抓不到时自动回退：

```python
data = _capture_joblist(page, lambda: page.goto(...))
if data is None:
    yield from _iter_jobs_dom(...)      # 接口改版/被拦，退回解析 DOM
    return
```

兜底路径下薪资是密文、公司规模为空，对应的过滤规则会因此拒绝这些岗位
——**宁可漏发不可错发**。

## 三、选择器：候选列表 + 自检

详情页和聊天区必须解析 DOM（没有对应接口）。这里的问题是 BOSS 前端改版频繁，
单一选择器随时会失效。

处理方式是**每个字段配一个候选列表**，全部集中在 `selectors.yaml`：

```yaml
detail:
  chat_button:
    - "a.btn.btn-startchat"          # 最精确，优先
    - ".btn-startchat"               # 去掉标签名，容忍元素类型变化
    - "a:has-text('立即沟通')"        # 按文案找，容忍 class 全改
    - "button:has-text('立即沟通')"
```

候选顺序是有讲究的：**从精确到宽松**。前两条基于 class，改版易失效但快且准；
后两条基于**可见文案**——class 可以随便改，但按钮上写的字不会变，
这是最后一道防线。

查询函数按顺序试，返回第一个命中的：

```python
def first_match(scope, candidates, timeout=3000) -> Locator | None:
    for sel in candidates:
        try:
            loc = scope.locator(sel).first
            loc.wait_for(state="attached", timeout=timeout)
            return loc
        except (PWTimeout, Exception):
            continue
    return None                  # 全部失效
```

配套的 `boss doctor` 命令会打开真实页面，逐条验证每个字段能否命中，
并指出**实际生效的是哪一条**：

```
│ detail.chat_button   │ ✅          │ a.btn.btn-startchat             │
│ list.activity        │ ❌ 全部失效 │ —                               │
```

看到 ⚠ 降级就知道首选失效了、该把生效那条提到前面；看到 ❌ 就知道该去
`boss dump` 存份 HTML 找新 class。**改版时改 YAML，不动代码。**

## 四、找到并点击「立即沟通」

### 页面状态的前提

`fetch_jd` 抓完 JD 后**页面就停在详情页**，不会导航走：

```python
def fetch_jd(page, sel, job) -> str:
    page.goto(job.url, wait_until="domcontentloaded")
    page.wait_for_timeout(1200)
    parts = texts_of(page, sel.get("detail.jd"))
    return "\n".join(parts).strip()
    # 页面留在详情页，供后续点「立即沟通」复用
```

这样点按钮时不用重新导航——少一次页面加载，也少一次被风控注意的机会。

### 点击前先看有没有风控

```python
def _open_chat(ctx, page, sel, job):
    _guard_risk(page, sel)          # ① 先扫风控文案
    btn = first_match(page, sel.get("detail.chat_button"), timeout=5000)
    if btn is None:                 # ② 按钮找不到
        _screenshot(page, job.job_id, "no-chat-btn")
        return None, "找不到「立即沟通」按钮（可能已沟通过或选择器失效）"
    try:
        btn.scroll_into_view_if_needed(timeout=3000)   # ③ 滚进视口再点
        btn.click(timeout=8000)
    except Exception as e:
        _screenshot(page, job.job_id, "click-failed")
        return None, f"点击沟通按钮失败：{type(e).__name__}"
    chat = _chat_page(ctx, page)    # ④ 确定接下来看哪个页面
    _guard_risk(chat, sel)          # ⑤ 点完再扫一次
    return chat, ""
```

几个细节：

**① 和 ⑤ 各扫一次风控**，因为提示可能是点击后才弹出来的：

```python
def detect_risk(page, sel) -> str | None:
    body = page.inner_text("body", timeout=2000)
    for phrase in sel.risk_texts:        # 「操作过于频繁」「安全验证」…
        if phrase in body:
            return phrase
    return None
```

命中就抛 `Circuit` 异常，整轮立刻停——继续点下去只会让账号更危险。

**③ `scroll_into_view_if_needed`** 不只是为了能点到。Playwright 对视口外的元素
会自动滚动，但那是瞬间跳转；显式滚动更接近真人「看到按钮→点击」的顺序。

**④ `_chat_page`** 处理一个不确定性：点击后可能原地弹窗，也可能新开标签页。

```python
def _chat_page(ctx, origin, timeout_ms=6000) -> Page:
    before = set(ctx.pages)
    origin.wait_for_timeout(1500)
    new_pages = [p for p in ctx.pages if p not in before]
    if new_pages:
        target = new_pages[-1]
        target.wait_for_load_state("domcontentloaded", timeout=timeout_ms)
        return target          # 新标签页
    return origin              # 原地弹窗
```

用「点击前后 `ctx.pages` 的差集」判断有没有开新页，比猜要稳。

## 五、发送确认：一个踩过的坑

这一节是整个项目最值得记的教训。

### 错误的假设

最初我以为点完「立即沟通」会打开聊天面板，于是去找「自己发出的消息气泡」：

```python
# ❌ 错误实现
if not _has_sent_bubble(chat, sel):          # 找 .item-myself .text
    return SendResult(False, "没看到平台自动发出的默认招呼语")
```

结果每个岗位都判失败，连续 3 次触发熔断：

```
熔断：连续 3 次发送失败，疑似被风控拦截。没看到平台自动发出的默认招呼语
```

### 实际行为

看失败截图（`data/logs/` 里存着）才发现：**消息全都发出去了**。

BOSS 点「立即沟通」的真实行为是：

1. **当场**把你在【消息通知-设置打招呼语】里设好的招呼语发出去
2. 弹一个 `已向BOSS发送消息` 的确认框，里面显示发出的内容
3. 页面**停在详情页**，不出现聊天面板
4. 按钮文案从「立即沟通」变成「继续沟通」

所以找气泡永远等不到——那个 DOM 结构在这个页面上根本不存在。

### 正确实现

认平台真正给出的信号，也就是那个确认框的文案：

```yaml
chat:
  sent_dialog_texts:          # 注意：这是页面文案，不是 CSS 选择器
    - "已向BOSS发送消息"
    - "已向Boss发送消息"
    - "消息已发送"
  stay_button:
    - "button:has-text('留在此页')"
```

```python
deadline = _DIALOG_WAIT_MS          # 6000ms
while deadline > 0:
    _guard_risk(chat, sel)          # 等的过程中也在盯风控
    if _sent_dialog(chat, sel):     # 确认框出现 → 成功
        _dismiss_dialog(chat, sel)
        return SendResult(True)
    if _has_sent_bubble(chat, sel): # 万一哪天真跳聊天页，气泡也算数
        return SendResult(True)
    chat.wait_for_timeout(500)
    deadline -= 500
```

**轮询而不是固定 sleep**：确认框是异步弹的，固定等 2.5 秒要么白等要么不够。
轮询最快 0.5 秒就能返回，最慢等满 6 秒。

**点掉确认框要点「留在此页」，不能点「继续沟通」**——后者会把页面带去聊天页，
下一个岗位的流程就乱了。点不到也无所谓，下一个岗位会 `goto` 新详情页，弹窗自然消失。

### 附带修正

同一个误解也影响了「自定义招呼语」那条路径——它找输入框，但详情页上没有：

```python
# 点完沟通平台会先自动发一条，并弹确认框，页面停在详情页。
# 要发自己写的这条，得顺着确认框里的「继续沟通」进聊天页，否则根本没有输入框。
if _sent_dialog(chat, sel):
    chat = _enter_chat_from_dialog(ctx, chat, sel) or chat

box = first_match(chat, sel.get("chat.input"), timeout=8000)
```

**教训：发送确认要认平台真正给出的信号，不要按「我以为它该怎么响应」去找。**
失败截图存在 `data/logs/` 就是为这种时候——一眼能看出是选择器失效、
被风控了，还是压根判错了。

## 六、反自动化

### patchright 而不是 playwright

```python
# 用 patchright 而不是 playwright：两者 API 完全一致，但 playwright 的 CDP 会话
# 带着 Runtime.enable 这类可被页面脚本探到的痕迹——实测 BOSS 的页面脚本一旦探到，
# 会在一秒内把整个标签页关掉（不管浏览器是不是用户自己开的）。
from patchright.sync_api import ...
```

`Runtime.enable` 是 CDP 协议的一个命令，Playwright 用它做 JS 执行上下文管理，
但它会在页面侧留下可探测的痕迹。patchright 是 Playwright 的一个 fork，修掉了这些泄漏。
API 完全兼容，改个 import 就行。

### 接管用户自己的 Chrome

更根本的做法是**不自己启动浏览器**：

```python
browser = pw.chromium.connect_over_cdp("http://127.0.0.1:9222")
ctx = browser.contexts[0]
```

用户先用调试端口启动自己的 Chrome、**手动**登录 BOSS，工具通过 CDP 连上去操作。
这样浏览器带着真实的历史、cookie、指纹、扩展——反自动化基本无从下手。
实测 `navigator.webdriver` 为 `false`，没有任何 `--enable-automation` 痕迹。

为什么必须这样：Playwright 自带的 Chromium 打开 BOSS 登录页，**两秒内整页刷成空白**，
二维码根本不渲染。自启模式下必须用 `channel="chrome"` 调本机真实 Chrome 才行。

两个配套细节：

- **必须独立的 `--user-data-dir`**。Chrome 136 起不允许对默认用户目录开调试端口。
- **退出时只断开连接，不 `close()`**——浏览器是用户开的，不该关人家窗口。
  也不抢占用户正在看的标签页（`page_of` 优先复用已停在 BOSS 上的页，没有就新开）。

### 输入节奏

```python
def human_type(loc, text):
    """逐字符输入，字间随机停顿。整段 fill 的时序特征太机械。"""
    for ch in text:
        loc.type(ch, delay=random.uniform(30, 110))
```

`fill()` 是瞬间设值，时序上一眼假。逐字符 + 随机间隔更像人打字。

### 发送间隔

详见 README 的[账号安全](../README.md#账号安全)一节。要点是
**真正的约束是「每小时发多少」，不是每天发多少**——实测一小时 42 条被强制登出，
而且并没有触发「今天聊天过多了」的次数上限。

## 七、完整时序

```
iter_jobs(keyword)
  ├─ page.goto(搜索URL)  ──旁听──▶ joblist.json  ──▶ parse_api_job × 15
  │                                                    ↓
  │                                            列表页初筛（免费规则）
  │                                                    ↓ 通过的
  ├─ fetch_jd(job)  ──▶ page.goto(详情页) ──▶ .job-sec-text
  │                     【页面停在详情页】             ↓
  │                                            详情页复筛 + AI 判定
  │                                                    ↓ 通过的
  └─ send_default_greeting(job)
       ├─ _already_chatted?  按钮是「继续沟通」→ 跳过
       ├─ _guard_risk        扫风控文案
       ├─ first_match(detail.chat_button)   4 个候选依次试
       ├─ scroll_into_view → click
       ├─ _chat_page         点击前后 ctx.pages 差集 → 新标签页 or 原地
       ├─ 轮询 6s：出现「已向BOSS发送消息」→ 成功
       ├─ 点「留在此页」关弹窗（不是「继续沟通」）
       └─ 入库 status='sent'  ← 去重只认这个状态
```

## 八、代码地图

| 文件 | 职责 |
|---|---|
| `browser.py` | 浏览器接管/启动、容错查询（`first_match`）、风控检测、拟人输入 |
| `scraper.py` | 旁听列表接口、接口字段→Job、DOM 兜底解析、JD 提取 |
| `sender.py` | 点「立即沟通」、确认框识别、两条发送路径 |
| `filters.py` | 规则过滤链（纯函数，可完整单测） |
| `screener.py` | AI 读 JD 判外包/销售 |
| `greeter.py` | LLM 写招呼语 + 三道校验 |
| `pacing.py` | 随机延迟、分批休息、熔断 |
| `runner.py` | 主流程编排 |
| `selectors.yaml` | 所有 DOM 选择器（改版时只改这里） |

104 个单测全部不碰浏览器、不打网络——过滤链、薪资解析、招呼语校验、
标签解析、发送确认逻辑都是纯函数或可注入假对象的。
